What to run, in what order, and what each round decides. Consolidates the
validation plans from doc/RUNTIME_GUARDS.md, doc/INTENSITY_AUDIT_2026-07-09.md,
doc/STATUS_2026-07-09_lidarimg_crash_hunt.md, and doc/FUSION_ARCHITECTURE.md,

## Round 0 — Guards no-op check (BLOCKING, cheap)

**Substrate**: 06042026, clean-load reps the baseline handles. n ≥ 12.
**Stack**: `ouster_tunnel.yaml` + `ouster_06042026_extrinsics.yaml` +
`ouster_tunnel_xicp.yaml` + **`ouster_tunnel_guards.yaml`**.

**Pass criteria (all must hold):**
- `Physics Fuse Trips (cumulative)` == 0 on every rep,
- `Slosh Guard Activations (cumulative)` == 0 on every rep,
- DIV/slosh verdicts statistically indistinguishable from the same stack
  without the guards overlay (the guards must be a literal no-op on healthy
  runs).

**If it fails**: a guard is firing on healthy operation — do NOT proceed to
round 1. Fuse trips ⇒ raise `odom/fuse/maxStep*` (check what step tripped:
the ERROR log throttles at 1/s). Slosh activations ⇒ raise
`odom/slosh/engageFrac` / `minActive` or the deadband. Re-run round 0.

Also record here (free, same runs): `Lidar Image Az-Grad Energy` over the
in-tunnel segment — this is the graffiti-hypothesis number round 3 needs
(healthy texture O(0.01–0.1); ~0 kills arm B/C before they start).

  leg-1-style runaway),
- B: A + `ouster_tunnel_guards.yaml`.
- (keep `use_lidar_image` OFF — quarantined until round 2 clears it.)

**Metrics**: max|x| (fuse should cap the excursion at trips × maxStepTrans
growth instead of 3.3e7 m), `revs`/straightness vs leg 3's 58/0.012,
`Physics Fuse Trips` + `Slosh Guard Activations` against the failure
timeline (the trip timestamps double as instrumentation: when did the
estimator go implausible?).

**Decision**: guards reduce worst-case excursion and reversal count without
new failure modes ⇒ keep the overlay in the default tunnel stack going
forward. If positive, run the per-mechanism isolation (overlay header knobs:
fuse-only / slosh-only / velDamp-only) at n ≥ 6 each to attribute the effect
before tuning any values.

## Round 2 — Crash root-cause (unblocks imageRefs)

Per doc/STATUS_2026-07-09_lidarimg_crash_hunt.md: run the ASan/gdb
combo-hunt harness (`dliio_asan_combo_hunt.sh`, `dliio_gdb_hunt.sh`) against
the exact repro: `use_lidar_image:=true`, bag `07052026_4_an`,
`dlio_07052026.launch.py`. This repro fires in ~108 s–10 min — the best
sanitizer bait the campaign has had.

Also (cheap, first): grep the two existing crash-run logs for
`MEMORY-CORRUPTION SENTINEL` — if the June sentinel fired pre-crash, the
scribbler reaches the correspondence buffers too; silence localizes it to a
different heap region. Note: the decoded crash numbers are float bit
patterns (crash 1's `__n`/size pair decode to −0.0034/+0.0032 — residual/
image-magnitude data over a vector control block), consistent with the
still-open June OOB-float-writer rather than a new indexing bug. ASan
decides.

**Exit criteria**: a stack trace naming the writer, a fix, and the repro
surviving 3 consecutive full-bag runs under ASan. Until then
`odom/lidar_image/imageRefs` and `use_lidar_image:=true` stay quarantined.
