# 07052026_4_an live-RViz smoke test (2026-07-09)

Bag: `07052026_4_an` (raw-packet Ouster OS-1-64 + Lucid camera, 552.6s).
`dliio_ws:latest` rebuilt at submodule 72f75b9 (picks up the pre-voxel
intensity-reference + X-ICP partial-budget commits, see
`INTENSITY_AUDIT_2026-07-09.md`). n=1 each (live RViz, real-time, killed on
visual confirmation of failure — not a distribution, just first-look smoke
tests per the audit doc's own "smoke-test first" ask). Harness:
`scripts/dliio_07052026_rviz.sh` (new; sibling of `dliio_tunnel_rviz.sh` for
this bag's raw-packet decode + `dlio_07052026.launch.py`/
`dlio_07052026_notunnel.launch.py`).

Prior data point (8fc433f, 2026-07-08): tunnel-mode + `use_xicp:=true`
diverged worse than the un-intervened baseline, undiagnosed. All three legs
below are new data points beyond that one.

## Leg 1 — `dlio_07052026.launch.py` baseline (tunnel-mode, all use_* off)

`ouster_tunnel.yaml` + `ouster_07052026_extrinsics.yaml` (+ visual/lidarimg/xicp
overlays present but their enable flags forced off). **Catastrophic runaway**:
killed by the user mid-run ("horrifically diverged"); last recorded pose
**[3.29e7, -5.83e6, -2.95e7] m**. Repeated `IMU data does not cover the scan
period` warnings and the gate holding 1-2 axes throughout — this is a clean
monotonic blow-up, not bounded slosh.

## Leg 2 — same + `use_lidar_image:=true` (new pre-voxel `imageRefs`)

Same base + the new COIN-LIO map-term with keyframe-image references
(`odom/lidar_image/imageRefs: true`, `INTENSITY_AUDIT_2026-07-09.md` fix #3 —
the first real-bag exercise of that code path; the audit doc explicitly
flagged it as unvalidated). **Crashed** ~108s into playback:

```
terminate called after throwing an instance of 'std::out_of_range'
  what():  vector::_M_range_check: __n (which is 18446744072558204407) >= this->size() (which is 995238912)
[ERROR] process has died [pid 8414, exit code -6 (SIGABRT)]
```

`__n` is `2^64 - 1151347209` — an unsigned-underflow pattern (some index
computed as a negative offset, wrapped). A "size" of 995M elements is not a
plausible real container size here, which points at a corrupted vector
control block (stray write) rather than a legitimate off-by-one. Same
`std::out_of_range`-from-nowhere signature as the still-open
`FINDINGS_2026-06-25`/2026-06-26 photometric-loop crash — but `photometricWeight`
is 0 throughout this config chain (that term is inactive), so if related it's
the same underlying race manifesting through a different term, not the same
code path. **Needs the ASan/gdb crash-hunt harness** (`dliio_asan_combo_hunt.sh`,
`dliio_gdb_hunt.sh`) run against this exact repro before this dataset is
touched with `use_lidar_image:=true` again.

Preceded by the same `IMU data does not cover the scan period` + `degenerate
along 1-2 direction(s)` warnings as leg 1, no obvious behavioral change before
the crash — doesn't look like the crash was a consequence of an
already-diverged state.

## Leg 3 — `dlio_07052026_notunnel.launch.py` (new; plain `dlio.yaml` + extrinsics only)

New isolation launch file (no `ouster_tunnel.yaml` or any `tunnel_*` overlay —
just `dlio.yaml` defaults + `ouster_07052026_extrinsics.yaml`, which is
load-bearing regardless of tunnel-mode: without it the unapplied 180° yaw
between `os_lidar`/`os_imu` and the `base_link` frame collision with this
bag's own rig TF tree are still live bugs). Goal: isolate whether
`ouster_tunnel.yaml`'s 06042026-tuned gate/regularization/photometricWeight/
maxCorr numbers are actively harmful on this bag, vs. plain defaults.

**Result: still bad, different failure shape.** The degeneracy gate fired
just as often WITHOUT the tunnel overlay (confirms the gate itself is a
`dlio.yaml` default, not something `ouster_tunnel.yaml` turns on — only the
threshold ratio differs). Trajectory stayed bounded (~tens of meters) for
roughly the first third of the bag, then one large slew, then a violent
back-and-forth oscillation. Killed by the user once visually confirmed bad
(36918/37568 poses captured, ~98% of the bag). `analyze_traj.py` verdict:

```
finalX=-456.0  maxX=6894.7  revs=58  fwd/back=36296/36752  path=173295  straight=0.012  -> SLOSH_HI
```

58 reversals and straightness 0.012 (net displacement / path length) is
severe oscillatory slosh — arguably a *worse-shaped* failure than leg 1's
clean runaway even though its peak excursion (6.9 km) is three orders of
magnitude smaller than leg 1's (33,000 km-equivalent). Conclusion:
`ouster_tunnel.yaml`'s tuned parameters are not the (sole) source of leg 1's
catastrophic blow-up — removing them changes the failure mode's shape but
does not fix the dataset. The along-axis degeneracy is a genuine property of
this bag's environment, not an artifact of 06042026-tuned overlay numbers.

## Leg 2 follow-up — code reading + a real (but insufficient) fix

Read through the `imageRefs` data path end-to-end (`sampleKeyframeLidarRefs`,
`buildSubmap`'s concatenation loop, `accumulateLidarMapResidual`). Found and
fixed a genuine unlocked data race in `buildSubmap()` (odom.cc:3625-3634):
`build_visual_refs`/`build_lidar_refs` read `this->keyframe_{visual,lidar}_refs.size()`
and `this->keyframes.size()` on the background `buildKeyframesAndSubmap`
thread WITHOUT holding `keyframes_mutex`, while `updateKeyframes()` on the main
thread does `push_back` on these same vectors UNDER that lock — a
push_back-triggered reallocation racing this unlocked `.size()` compare can
tear the read. Fixed by moving both comparisons inside a
`lock.lock()`/`lock.unlock()` pair. Also hardened `keyframe_lidar_refs[k]` to
`.at(k)` (odom.cc:3656-3659) so a future recurrence throws immediately with a
precise index/size instead of silently propagating a garbage `shared_ptr`.

**Rebuilt and re-ran `lidarimg` live: crashed again.** Same
`std::out_of_range` signature, different (still nonsensically large) numbers:
`__n=1972129020 >= size=381691607` (previously `__n≈1.8e19, size≈9.95e8`),
exit -6, this time ~10 minutes in rather than ~108s. Both crashes' numbers are
implausible for any real container in this pipeline (hundreds of millions to
quintillions of elements), consistent with reading a corrupted/dangling
vector control block rather than a legitimate off-by-one — but since neither
crash log includes a stack trace, and there are ~15 other `.at()`/`->at()`
call sites in the `lidar_image` path (`accumulateLidarMapResidual`'s
`target_->at(j)`, `sampleKeyframeLidarRefs`'s `cloud->at(i)`, several
`organized->at(col,row)` in the image-build functions), it's not possible to
confirm from these logs alone whether the race just fixed was the actual
cause, a partial cause, or unrelated to this specific crash.

**The race fix is being KEPT** (it's a real bug independent of whether it's
the crash's root cause — an unlocked `.size()` read against a concurrently
`push_back`-mutated vector is UB regardless of outcome) but is **uncommitted**
in the `src/dliio` working tree pending further verification.
**Next step: the ASan/gdb combo-hunt harness** (`dliio_asan_combo_hunt.sh`,
`dliio_gdb_hunt.sh`) is needed for a definitive stack trace — static reading
has hit diminishing returns on pinpointing which of the many `.at()` sites is
actually throwing.

## Takeaways

- **07052026_4_an is not currently tractable for dliio in any tested
  configuration.** Three legs, three failure modes (clean runaway / crash /
  violent slosh), none bounded-and-tracking.
- The `use_lidar_image:=true` crash is the most actionable finding — a
  reproducible (this session) crash in the brand-new, previously
  bag-unvalidated pre-voxel `imageRefs` code, needing sanitizer/gdb root-cause
  before that code path is trusted on any bag.
- Isolating `ouster_tunnel.yaml` (leg 3) does not rescue this dataset;
  the degeneracy is structural, not a parameter-tuning artifact.
- No leg here used `use_xicp` (the one lever validated to *prevent* — not
  just bound — the 06042026 collapse) in isolation from the rest of
  `ouster_tunnel.yaml`; 8fc433f's negative result bundled X-ICP with the full
  overlay. Still open per that commit: "needs a follow-up run isolating
  X-ICP alone."
