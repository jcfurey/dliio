# Findings 2026-06-18 — clean-harness n=5 sweep: the auxiliary terms destabilize the tunnel

Evaluation of the robustness features added on `lyrical` through `5d4691d`
(sub-floor reject, margin-adaptive clamp, probabilistic gate, adaptive Barron
kernel) on the 06042026 Ouster conduit/tunnel, using a **rebuilt measurement
harness** (see the test workspace `resple_test_ws`). Supersedes the single-run
reads in `FINDINGS_2026-06-17.md`, which were confounded by a measurement
artifact and by run-to-run chaos.

## Why the earlier numbers were untrustworthy (now fixed)

1. **Post-bag artifact.** The replay scripts kept recording for ~8 s after the
   bag ended; with no data the node IMU-integrates into runaway, and those
   post-playback poses were folded into `final_x` / `max|x|` (producing the
   bogus +50 000 m endpoints). The harness now records a wall-clock receive
   sidecar and clips to the playback window — **all metrics are in-bag only.**
2. **Sim-time matters.** Running wall-clock (no `--clock`) measurably worsens the
   chaotic trajectory (maxX 186 vs 74 sim-time on the same config). All results
   below are sim-time + `--clock`.
3. **Chaotic basin.** A *fixed* config (baseline) spans `final_x` −50 … +79 m
   across 5 reps. **Single runs are meaningless; n ≥ 5 distributions are
   mandatory** — and even n = 5 may not separate basin-noisy configs.

## Results (n = 5 unless noted; headless solo, sim-time, in-bag metrics)

| config | verdicts | max\|x\| med | straight | note |
|---|---|---|---|---|
| **baseline** (geom + extrinsics) | SLOSH:4 SHORT:1 | 43 m | 0.32 | **only stable config** — never DIV; always ping-pongs |
| **lidar_image** (`ouster_tunnel_lidarimg.yaml`, w 0.05) | SLOSH:3 **DIV:2** | 61 m | 0.45 | **worse than baseline** — injects divergence (975/1048 m, both `deg=6`); non-DIV runs just match baseline |
| **camera visual** (`ouster_tunnel_visual.yaml`, w 0.5) | DIV (n=1) | broken | — | **Visual Points = 0** (Phase-2 bug) *and* starves the pipeline (`starve=6`) → DIV |
| **photometric** (gicp) | DIV (n=1, prior) | — | — | n=5 deferred; earlier single-runs diverged |

`SLOSH` = ping-pong (low straightness); `SHORT` = barely moved; `DIV` =
max\|x\| > 200 m. No run showed CPU starvation except the camera term, so the
divergences are the *terms* destabilizing the solver basin, not load.

## Per-feature read (`5d4691d`)

- **Sub-floor reject (#1)** — **0 points rejected** on this bag at default params
  (margin 0.30, radius 8.0): a no-op here. It targets the water-pool *drag-down*
  (mirror returns below the floor), not the along-axis ping-pong. Mechanism
  verified live (the keep-mask runs every scan, diagnostic published); there is
  simply nothing matching its signature on this segment.
- **Margin-adaptive clamp (#2) / base `maxCorr*` clamp** — a *global magnitude*
  limiter. It shrinks each per-scan correction (smaller jumps) but cannot fix the
  *directional* degenerate-axis ping-pong: the degeneracy gate already **fully
  holds** the IMU prior on the flagged axis (warns every scan) and it still
  sloshes, because the IMU prior alone cannot pin the scale (a hard clamp →
  unbounded forward IMU drift). Clamping is not a substitute for an observation.
- **Probabilistic gate (#3)** — not isolated this session.
- **Adaptive Barron kernel (#5)** — **does not engage and makes things worse.**
  `Photometric Kernel Alpha` stayed pinned at **2.000 (L2) the entire run**: the
  residual bulk (RMS ≈ 0.025) is far below the scale `c = photometricHuberDelta =
  0.05`, so L2 is genuinely NLL-optimal for the bulk and the few specular
  outliers don't pull the fit. Worse, enabling the kernel **replaces** the fixed
  Huber, and at α = 2 the Barron weight is 1.0 — so it **strips the Huber
  protection and adds nothing**, driving divergence (the run blew up harder than
  plain weight-1.0). **Fix:** set `adaptiveKernel/scale` ≪ 0.05 (so more
  residuals read as outliers) and/or cap `alphaHi` < 2; consider keeping the
  Huber as a floor when the kernel is on.

## Conclusion

Every auxiliary constraint term — reflectivity-photometric, camera-visual,
lidar-image — either **destabilizes the chaotic tunnel basin into divergence or
is broken**. Only **geometry + gate** stays bounded (and it ping-pongs along the
unobservable axis). A scalar weight does not reliably move the divergence basin;
this is now confirmed at n = 5 with a clean harness, consistent with the earlier
low-n caveats in `ouster_tunnel_lidarimg.yaml`.

The along-axis tunnel degeneracy is **not solved by any current term.** The
highest-value next step is the **Phase-2 camera visual term**: it is the only
term that could add genuinely independent along-axis information (wall texture),
but it currently emits zero points and must be debugged (image time-matching /
projection / keyframe refs) before it can even be evaluated.

Confirmed sound this session: the 180° IMU-yaw extrinsic fix (verified applied 3
ways, incl. live `baselink2imu/R = diag(-1,-1,1)` and forward IMU dead-reckoning)
and the voxel photometric fix (reflectivity channel alive, ~1100 pts/scan).
